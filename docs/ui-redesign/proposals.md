# BiliSail 界面改版候选方案

日期：2026-10-25。状态：**用户已选择晴湾，实施以最新确认和[实施记录](implementation.md)为准。**

最新确认：桌面直播独立，番剧／国创／放映厅继续放在首页，不设置影视一级入口或媒体库；窄屏底部仅首页、动态、我的、设置，直播与影视频道归入首页。现有视频卡与所有业务功能保留。以下候选方案保留用于记录设计选择，早期预览不是最终导航规范。

第二轮确认：桌面双标签使用一个浏览主窗口和一个独立播放窗口，视频/影视/直播共用后者，不保留顶部双标签栏；正式图标、底部固定入口、页面工具栏与独立“我的”页按[第二轮方案](refinement-plan.md)实施。下文同窗双标签与嵌入账号面板的候选描述已由该确认替代。

第三轮确认：移除单标签模式，旧设置迁移双标签；播放窗返回移入原生标题栏并保留用户尺寸；首页保留头像搜索、移除三个快捷工具；我的页直接以历史／稍后再看／收藏／下载四个内容标签展示。以[第三轮方案](third-round-plan.md)为准，下文单标签与账号入口卡均为历史候选。

第四轮确认：首页、动态、直播、我的同层且共用固定根标签；双标签返回关闭离开的临时页面，媒体历史耗尽关闭播放窗。桌面直播直接展示推荐／关注／观看记录并保留头像搜索，消息使用共享标签条；热门补齐每周必看、入站必刷并合入排行榜。以[第四轮方案](fourth-round-plan.md)为当前规范，保留的早期静态预览不代表最终栏目或返回行为。

本轮目标是统一视觉层级、改善桌面与窄屏布局，保留全部现有功能；另将用户补充的“双标签模式”作为独立功能提案。三套视觉方向均兼容单标签、多标签和候选双标签模式。预览中的内容、计数、账号与播放画面用于展示布局，不连接账号服务，不发送评论、弹幕或私信。

## 2. 三套方案

### 晴湾 · 轻盈分区（推荐）

**定位：有品牌辨识度，适合长期日常使用。**

- 桌面：分组侧栏 + 工作区标签 + 独立内容面板。首页、动态、直播、我的为主要分组；消息、下载与设置位于其后。影视频道放在首页，不设媒体库；中等宽度收为导航轨。
- 首页：标题、频道、内容三级。封面保持 16:9，标题两行，UP／时间弱化；只有封面做圆角，不把每个视频都装进带边框的大卡片。
- 播放：保留左右分栏。播放器下方组织标题与互动，右侧放作者、选集／队列和推荐；评论、简介保留已有切换和滑动能力。
- 移动：底部“首页／动态／我的／设置”，首页包含直播、番剧、国创和放映厅，顶部保留账号与搜索；二级分类横向滚动。播放详情收起底部主导航，用返回与工作区入口回到浏览。
- 配色：淡蓝灰背景 + 实色白面板 + 项目玫红强调色。深色转为蓝灰层次，不反转视频画面和封面。
- 建议 token：页面外边距 24／移动 14–16；卡片横距 18、纵距 24；封面圆角 12–14、面板 18、控件 10；普通正文 14–15。
- 取舍：层级最清楚，桌面左侧占用少量宽度；比现状减少同屏卡片数量。窄桌面自动收窄侧栏，不强行压缩正文。

### 素白 · 高效浏览

**定位：接近参考图二，信息密度优先，迁移成本相对较低。**

- 桌面：64–72 宽导航轨 + 紧凑顶部工作区／搜索 + 下划线频道。保持大面积纯净背景，分隔线只用于层级边界。
- 首页：规则密集网格；常用桌面宽度比晴湾多一列。取消过大的卡片外壳，保留封面、标题、UP 与必要角标。
- 播放：侧边信息分组更紧凑。操作区保持单行优先，放不下再收进具名菜单；不能缩小触摸区域或隐藏关键播放能力。
- 移动：双列视频网格和五项底部导航；二级分类与筛选分行，避免频道／搜索／账号挤成一行。
- 配色：中性白／浅灰 + 现有玫红；深色为中性炭灰。风格重在排版，不依赖半透明。
- 建议 token：页面边距 20–24／移动 12–14；卡片横距 16、纵距 22–24；封面圆角 8、控件 8；卡片标题 14、元信息 12。
- 取舍：最容易快速扫大量内容；个性相对克制，需要依靠准确的字重、间距与选中态体现精致度。

### 映厅 · 内容优先

**定位：大封面、弱工具感，适合长视频和追番。**

- 桌面：移除常驻侧栏，主导航进入顶部；工作区标签仍独立存在。内容区居中、限制最大宽度，大封面三列为主。
- 首页：放大内容卡片，保留真实推荐流顺序；不新增自动播放横幅、编辑精选或未经实现的数据推荐模块。
- 播放：默认宽播放器，简介／评论和选集／推荐组织在下方；仍提供切回侧栏布局的入口。直播应优先保留右侧聊天，不能为了观影布局藏起实时互动。
- 移动：单列大封面为主要视觉区别；底部导航与其余方案一致。列表密度需作为后续可选偏好评估，不能强制覆盖已有用户设置。
- 配色：浅色暖白／石色，深色炭黑／暖灰；低饱和暖色强调。播放区域保持黑色，文字与互动区域按应用主题显示。
- 建议 token：页面边距 28–32／移动 14–16；卡片横距 24、纵距 28；封面圆角 12、表单 10；卡片标题 15–16。
- 取舍：内容沉浸感强，搜索和内容管理的效率略低；消息、下载、设置仍使用清晰列表，不套大封面排版。

以上为候选产品 token，不是 Flutter 固定规范。三套方案都提供浅／深色，并继承用户字体。无需把它们全部做成应用内皮肤，选择一套整体语言后统一实现即可。

## 4. Flutter 自适应策略

布局按 **分配给组件的可用逻辑宽度** 决定，不以 Windows／macOS／Android 或横竖屏硬切三套 UI。`LayoutBuilder` 判断局部空间，`MediaQuery.sizeOf`、`paddingOf`、`viewInsetsOf` 分别处理窗口、安全区和键盘；平台差异只放在标题栏／窗口能力／输入适配器。采用 Flutter 官方建议的“共享数据、测量、选择呈现”流程：[自适应通用方法](https://docs.flutter.dev/ui/adaptive-responsive/general)、[最佳实践](https://docs.flutter.dev/ui/adaptive-responsive/best-practices)。

| 可用宽度（提案） | 导航与主体 | 播放／详情 |
| --- | --- | --- |
| < 600 | 底部 NavigationBar；纵向主体；发现频道可横向滚动 | 上下布局，单列信息；短横屏按高度进一步收紧控件 |
| 600–839 | NavigationRail；按卡片最小宽度排 2–3 列 | 通常上下布局，避免侧栏挤压画面 |
| 840–1199 | 晴湾可扩展侧栏，素白保留轨，映厅保留顶栏 | **局部**空间够放播放器最小 560 + 信息区最小 300 + 间距时才并排 |
| ≥ 1200 | 舒适边距与自适应列数；内容宽度上限约 1680 | 侧区建议 320–380，播放器占剩余；观影布局按用户选择 |

这些是待 Flutter 原型验证的设计断点，不声称系统会自动替开发者选择导航布局。`Expanded`／`Flexible` 负责剩余空间，`ConstrainedBox` 防止表单／长文本无限拉宽；共享 `SliverResponsiveCardGrid` 继续按文字缩放计算自然行高，不换成可能截断大字标题的固定高度网格。

Windows 和 macOS 共用内容布局。Windows 留出窗口按钮与拖动区；macOS 避让原生左上角按钮并处理原生全屏。Android 使用 SafeArea、系统返回／预测性返回与键盘避让；折叠屏与分屏同样按可用空间重排。原生平台行为须后续分别验证，视觉预览不代表通过。

导航模式是持久偏好，宽度变化只改变其呈现。Android 用户选择多标签时仍能访问全部标签；桌面用户选择单标签时仍按访问栈返回。不可因切断点销毁 ProviderScope、播放器、滚动位置、当前页或草稿。

## 5. 双标签模式提案

### 5.1 用户可见规则

最多显示两个工作区标签：**浏览** 与 **播放**。没有打开媒体时只显示浏览；播放标签在首次打开视频／PGC／直播／离线媒体时建立。

1. 推荐、排行榜、直播推荐、动态、搜索、收藏、UP 主页、下载、消息、设置在“浏览”标签内导航，保留各自访问和滚动状态。
2. 从浏览列表打开媒体，选中“播放”；浏览列表、筛选、搜索词保持原样。用户切回浏览可继续找内容，不会关闭播放标签。
3. 播放页中点开另一视频，复用同一播放标签；切换前保存当前位置和返回快照，成功选中目标后更新标签标题。
4. 播放标签内的“上一视频”返回最近一次显式打开的媒体，恢复其位置和可用播放选项。对直播只返回房间与选择，不伪造可回放进度。
5. 关闭播放标签，释放该标签的会话并清除其播放返回历史，回到当前保留的浏览页；不是强制跳首页顶部。下载任务继续。
6. 播放历史为空时，返回回到浏览，不自动关闭播放标签。提供单独的关闭入口；“返回”与“关闭”是不同动作。

示例：推荐滚动到第二屏 → 打开视频 A → 在 A 的相关推荐打开 B → “上一视频”回 A 原位置 → 关闭播放标签 → 推荐仍在第二屏。

### 5.2 播放历史与队列区分

| 动作 | 播放返回历史 |
| --- | --- |
| 用户显式点开另一个视频、番剧或房间 | 保存当前条目并进入新条目 |
| 重复打开当前同一内容 | 选中现有条目，不重复压栈，不重新解析 |
| 自动下一集、下一 P、队列自动推进 | 更新当前连续播放条目，保留队列上下文，不逐项压栈 |
| 手动选择同一视频的分 P／同一番剧选集 | 更新当前条目内的位置，不新增工作区导航记录 |
| seek、清晰度、倍速、线路、URL 刷新 | 不改变返回历史 |
| 返回上一条后再打开新内容 | 沿新的访问路径追加；本轮不增设未实现的前进按钮 |

关闭、返回、上一集分别有明确语义。空降、章节跳转和恢复播放不应影响导航历史。

### 5.3 状态与资源边界

- 双标签是 `WorkspaceNavigationMode` 的第三个值，和视觉方案解耦；不是“最多开两个普通标签”的限制开关。
- 播放标签只拥有一个 `PlaybackSession`／engine。历史只保存稳定内容身份、确认位置、选集／队列上下文、可恢复选择与播放意图，不为历史项保留额外 engine，不保存带签名媒体 URL 或凭据。
- 候选历史上限为 **16 条媒体快照**，浏览页面与访问历史沿用既有 **16／64** 上限。具体对象共享方式在实施前对照 WorkspaceController 确定，不把这些上限叠成无限缓存。
- 使用已有取消、source generation、互斥许可、换源与有界恢复机制。A→B→C 快速打开时只允许 C 提交新状态，旧响应不能覆盖 C。
- 返回前保存当前确认位置，再通过现有 resolver 重新获取可用媒体源。权限、账号或本地文件变化按原错误分类显示；失败时保留浏览入口和可重试的目标快照。
- 从播放切到浏览沿用现有“普通页面切换”的播放意图规则；隐藏 surface／快捷键不等于关闭媒体。手动暂停不自动恢复；应用进入系统后台继续按现有平台策略执行。
- 双标签最多一个播放会话，因此“允许多标签同时播放”在此模式不生效，但保留用户存储值，切回多标签继续沿用。不得在 UI 中暗示双标签支持并发。
- 切换主题、窗口大小、显示导航形式不能重建会话。全屏只是同一媒体的呈现变化。

### 5.4 单／双／多标签切换

设置“外观 → 导航模式”提供三项。首次默认暂保持现有平台策略，**不自动把老用户切到双标签**。

- 单→双：当前媒体进入播放槽，当前或最近浏览页进入浏览槽；保留页面身份和状态。
- 多→双：当前播放页（否则最近播放页）作为唯一活动播放槽，其余未关闭页面保留在既有有界缓存中，其他媒体暂停，不并发。
- 原多标签页面集在模式切换期间保留，切回多标签可恢复原标签及其页面状态。若在双标签中明确关闭某内容，按关闭语义处理，不能切回时复活。
- 双→多：浏览和当前播放成为原有工作区可访问页面，恢复尚未关闭的原标签；不会把播放历史 16 条全部批量开成标签。
- 双→单：当前页面成为单页前台，返回仍可回到浏览；媒体与导航快照通过既有缓存保留。
- 达到现有页面容量上限时沿用有界策略，不为“模式恢复”额外创建第二套无界页面集合。

该切换策略是下一阶段需要重点验证的设计点，不能只改枚举和标签外观。若当前控制器结构无法无损表达，先补小型纯 Dart 导航状态模型和行为测试，再接入呈现层。

### 5.5 窄屏与快捷键

- 双标签窄屏用一行“浏览／播放”紧凑切换器；标题过长截断，关闭按钮有独立触控区域。Android 默认单标签不改变，选择双标签才显示。
- 播放页的上一视频是可见按钮；系统返回先关闭弹窗／退出全屏，再按当前播放历史返回，最后回浏览。文本编辑时不拦截输入动作。
- `Ctrl+W` 和已有关闭命令关闭当前播放槽；浏览槽是保留入口，不能关闭后留下空白壳。侧键遵循用户已有绑定，不能擅自从“关闭”改成“返回”。
- `Ctrl+Tab` 等现有切标签命令在两个有效槽之间循环；不引入页面级全局键盘监听。

## 6. 共享视觉与交互规范

- 主次关系：选中态用强调色 + 形状／下划线，文本不靠颜色独自表达状态。每页只设一个主要内容标题，组标题与卡片标题按 24／18／14–15 的阶梯组织。
- 间距以 4 的倍数为主，卡片标题与元数据基线对齐。圆角按层级统一，不把所有元素都做成大胶囊。
- 封面固定比例，头像在首帧前保持固定尺寸空白；错误／无 URL 后备独立保留。加载骨架不得改变最终尺寸。
- 桌面悬停只改变局部表面和操作可见性，不驱动整页重建；触屏通过常显三点菜单访问同样操作。右键只做增强，不能成为唯一入口。
- 触摸目标建议不小于 48×48 逻辑像素；图标可以较小但有效命中区域不缩小。支持键盘焦点、Tab 顺序、读屏语义及 200% 文字缩放。
- 120–180ms 用于按压／选择反馈，180–220ms 用于轻量面板进入；减少动画偏好关闭位移。播放器 resize／全屏不做视频纹理缩放转场，不使用全屏实时毛玻璃。
- 表单错误、空列表、加载、网络失败、未登录、权限限制分别呈现；错误动作局部重试，不刷新整页或意外重放账户写请求。
- 设置保存立即应用；失败保留或恢复已保存值。新外观只改变缺失值的默认，保留有效字体、主题、弹幕和导航配置。

## 7. 建议落地顺序与验收

1. 用户选定主方案；确定是否采用候选双标签模式。选定前不修改生产 UI。
2. 先统一 `BiliTheme` 的 ColorScheme／TextTheme／组件主题及少量 ThemeExtension token；保留字体继承和播放器局部深色主题。
3. 修改共享 shell 与卡片、菜单、表单，再覆盖搜索／收藏／动态／消息／下载；避免逐页复制新布局。
4. 独立实现双标签导航状态与迁移。测试完成后再把紧凑切换器接入三种宽度呈现。
5. 视频／PGC／直播共用的布局和控件最后联调，保持页面身份、source generation、全屏 surface 所有权与弹幕时钟。
6. 按原检查脚本验证；原生播放路径实际改动时补受影响平台构建和原生回归。用户另行限定自行构建／实机验证时遵循其范围。

验收矩阵：320、360、390、600、768、840、1024、1440 宽；短横屏、125%／150%／200% 文本；浅／深色；键鼠／触控；游客／登录；单／双／多标签。

关键行为：双标签 A→B→返回 A→关闭→浏览原滚动位置；播放页切到浏览继续找内容；自动下一集不堆历史；快速开 A/B/C；账号切换；源失效；关闭请求未完成的目标；普通／全屏与 resize；设置模式来回切换；多标签暂停意图；评论／私信草稿；后台下载；直播读旧消息与 SC。

最初设计阶段交付三套可交互视觉预览与本设计文档；用户选择后的实现见[实施记录](implementation.md)。预览检查和 Flutter 测试、原生播放、真实账号、Android／macOS 实机、性能验收是不同层次，不能互相替代。
